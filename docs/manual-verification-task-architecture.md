# Manual Verification Checklist — Task Architecture

> Прогнать после деплоя в staging: `docker compose -f docker-compose.dev.yml up -d`
> Последовательно выполнить каждый сценарий S1–S21.

---

## S1 — Базовый чат

**Предусловие**: Приложение запущено, открыт браузер на http://localhost:8080

- [ ] Открыть новый разговор (кнопка "Новый чат")
- [ ] Ввести сообщение "Привет, как дела?" и отправить
- [ ] Дождаться потокового ответа ассистента (текст печатается по символам)
- [ ] Обновить страницу (F5)
- [ ] Убедиться что оба сообщения (вопрос и ответ) присутствуют в истории

**Ожидаемо**: Сообщения сохранились и отображаются корректно после перезагрузки страницы.

---

## S2 — Создание задачи из чата

**Предусловие**: Открыт чат, ассистент отвечает

- [ ] Ввести сообщение "Напомни мне завтра в 9 утра про встречу с командой"
- [ ] Дождаться ответа ассистента (агент должен вызвать TaskTool внутренне)
- [ ] Убедиться, что ассистент подтвердил создание задачи (сообщение вида "Задача создана")
- [ ] Открыть раздел "Мои задачи" (или написать "Покажи мои задачи")
- [ ] Найти созданную задачу в списке со статусом PENDING или SCHEDULED

**Ожидаемо**: Задача создана, видна в списке задач, в чате — читаемое подтверждение без raw JSON.

---

## S3 — Recurring task

**Предусловие**: Открыт чат

- [ ] Ввести "Каждую минуту присылай мне текущее время" (короткий интервал для теста)
- [ ] Дождаться подтверждения создания recurring задачи от ассистента
- [ ] Подождать 1-2 минуты
- [ ] Проверить, что в чат пришло автоматическое сообщение с текущим временем
- [ ] Написать "Отмени recurring задачу" и дождаться подтверждения

**Ожидаемо**: Recurring задача срабатывает по расписанию и доставляет результат в чат без участия пользователя.

---

## S4 — Task isolation

**Предусловие**: Открыт чат

- [ ] Создать любую задачу через чат (например, "Найди информацию о Python")
- [ ] Дождаться завершения задачи и уведомления в чате
- [ ] Проверить сообщение с результатом: убедиться, что оно не содержит raw JSON, системных промптов, внутренних tool call вызовов
- [ ] Открыть DevTools → Network и убедиться, что в SSE потоке нет внутренних артефактов задачи

**Ожидаемо**: Чат показывает только читаемый результат для пользователя, без внутренних деталей выполнения агента.

---

## S5 — Real-time notifications (SSE)

**Предусловие**: Открыт чат в браузере, SSE соединение активно

- [ ] Открыть DevTools → Network → фильтр "EventStream", убедиться что SSE соединение `/sse` или `/stream` активно
- [ ] Создать короткую задачу: "Посчитай 2+2"
- [ ] НЕ обновлять страницу — просто ждать
- [ ] Убедиться, что результат появился в чате автоматически (без F5)
- [ ] В DevTools проверить, что пришло SSE-событие с уведомлением о завершении задачи

**Ожидаемо**: Результат задачи доставлен через SSE push, страница обновилась сама без действий пользователя.

---

## S6 — Human-in-the-loop (approval)

**Предусловие**: Открыт чат, агент поддерживает approval flow

- [ ] Ввести "Проверь что 5 > 3 и спроси меня перед тем как дать ответ" (или аналогичный approval-сценарий)
- [ ] Дождаться вопроса от агента в чате (агент должен остановиться и запросить разрешение)
- [ ] Ответить "Да" или "Продолжай"
- [ ] Дождаться продолжения и финального ответа задачи
- [ ] Проверить в списке задач, что задача завершилась со статусом COMPLETED

**Ожидаемо**: Задача приостановилась, вопрос появился в чате, после ответа пользователя задача продолжилась и завершилась.

---

## S7 — Отмена задачи

**Предусловие**: Запущена активная задача (можно создать долгую: "Подожди 60 секунд и ответь")

- [ ] Убедиться, что задача запущена (статус RUNNING в списке задач)
- [ ] Написать в чат "Отмени последнюю задачу"
- [ ] Дождаться подтверждения отмены от ассистента
- [ ] Открыть список задач и убедиться, что статус задачи изменился на CANCELLED
- [ ] Убедиться, что агент больше не выполняет работу (нет активности в SSE)

**Ожидаемо**: Задача gracefully остановлена, пользователь получил подтверждение, статус в БД — CANCELLED.

---

## S8 — Parent-child tasks (иерархия)

**Предусловие**: Открыт чат, агент поддерживает spawn дочерних задач

- [ ] Ввести "Параллельно найди: 1) столицу Франции 2) столицу Германии 3) столицу Италии"
- [ ] Дождаться сообщения о создании родительской задачи и 3 дочерних
- [ ] Проверить в списке задач наличие parent задачи и 3 child задач
- [ ] Дождаться завершения всех child задач и появления итогового ответа от parent
- [ ] Убедиться, что итоговый ответ содержит результаты всех 3 поиска

**Ожидаемо**: Parent создал 3 child tasks, они выполнились параллельно, результаты собраны и доставлены как единый ответ.

---

## S9 — Child result injection

**Предусловие**: Выполнен S8 или создана новая parent-child иерархия

- [ ] Создать задачу с зависимостью: "Найди столицу Франции, затем найди достопримечательности этой столицы"
- [ ] Дождаться создания parent и child задач
- [ ] Дождаться завершения первой child (столица) и запуска второй child (достопримечательности)
- [ ] Убедиться, что вторая child использует результат первой (в ответе должен быть "Париж")
- [ ] Получить итоговый ответ с достопримечательностями Парижа

**Ожидаемо**: Результат child task автоматически доступен следующей задаче в цепочке через контекст parent.

---

## S10 — Progress updates

**Предусловие**: Открыт чат

- [ ] Создать долгую задачу с явным прогрессом: "Обработай последовательно 5 шагов, сообщай о каждом"
- [ ] Наблюдать за чатом без обновления страницы
- [ ] Убедиться, что промежуточные сообщения о прогрессе появляются в чате в реальном времени
- [ ] Дождаться финального сообщения о завершении задачи

**Ожидаемо**: Промежуточные progress-уведомления приходят через SSE в чат в реальном времени, пользователь видит ход выполнения.

---

## S11 — Error notification + audit access

**Предусловие**: Открыт чат

- [ ] Создать заведомо ошибочную задачу: "Вызови несуществующий инструмент FAKE_TOOL_XYZ"
- [ ] Дождаться уведомления об ошибке в чате (понятное сообщение, не стектрейс)
- [ ] Написать "Покажи детали последней ошибки" или "Что произошло с задачей X?"
- [ ] Убедиться, что агент вернул детали: время создания, что было отправлено в LLM, что ответила модель, описание ошибки
- [ ] Убедиться, что в основном чате нет сырого стектрейса — только понятное описание

**Ожидаемо**: Пользователь получил читаемое уведомление об ошибке, по запросу — полный audit trail из БД.

---

## S12 — Notify policy

**Предусловие**: Открыт чат

- [ ] Написать "Создай задачу молча: посчитай 1+1" (режим silent)
- [ ] Убедиться, что задача выполнилась, но уведомление в чат НЕ пришло
- [ ] Написать "Создай задачу и сообщи только об ошибке: посчитай 2+2" (режим on_error)
- [ ] Убедиться, что задача выполнилась успешно — уведомление НЕ пришло
- [ ] Создать ошибочную задачу с политикой on_error и убедиться, что ошибка всё же пришла

**Ожидаемо**: Notify policy соблюдается: silent — нет уведомлений; on_error — уведомления только при ошибках.

---

## S13 — Task timeout / watchdog

**Предусловие**: Приложение запущено, есть возможность создать задачу с коротким timeout

- [ ] Создать задачу с явным timeout: "Выполни задачу но сделай вид что она зависла" (или напрямую через API: POST /api/tasks с timeout_seconds=10)
- [ ] Подождать timeout_seconds + несколько секунд
- [ ] Проверить в списке задач, что статус изменился на FAILED с причиной "timeout"
- [ ] Убедиться, что в чат пришло уведомление "Задача X зависла и была остановлена"

**Ожидаемо**: Watchdog автоматически завершил зависшую задачу, пользователь получил уведомление.

---

## S14 — Startup recovery

**Предусловие**: Есть pending-уведомления в delivery_queue (можно создать задачу, дождаться завершения и заблокировать доставку)

- [ ] Создать задачу и убедиться, что она завершилась пока браузер был закрыт / SSE отключён
- [ ] Перезапустить приложение: `docker compose -f docker-compose.dev.yml restart app`
- [ ] Открыть браузер и подключиться к чату
- [ ] Убедиться, что пропущенные уведомления о завершённых задачах появились в чате
- [ ] Проверить в БД (или логах), что delivery_queue записи обработаны после старта

**Ожидаемо**: После рестарта сервера все pending уведомления из delivery_queue доставлены пользователям.

---

## S15 — Rate limiting

**Предусловие**: Открыт чат под обычным пользователем (не admin)

- [ ] Попытаться создать больше задач, чем разрешено лимитом (например, 10+ задач подряд быстро)
- [ ] Убедиться, что после превышения лимита агент возвращает сообщение об ограничении
- [ ] Убедиться, что лишние задачи НЕ были созданы (проверить список задач)
- [ ] Войти под admin-аккаунтом и убедиться, что лимиты для admin другие или отсутствуют

**Ожидаемо**: Rate limit соблюдается, пользователь получает понятное сообщение при превышении, задачи сверх лимита не создаются.

---

## S16 — Task context carry-over (recurring memory)

**Предусловие**: Открыт чат

- [ ] Создать recurring задачу: "Каждую минуту присылай случайное число от 1 до 10, не повторяй предыдущие"
- [ ] Дождаться 2-3 срабатываний (2-3 минуты)
- [ ] Проверить, что числа в ответах не повторяются
- [ ] Написать "Покажи историю рекуррентной задачи X" и убедиться, что видны предыдущие executions
- [ ] Отменить задачу

**Ожидаемо**: Recurring task помнит предыдущие executions и использует их в контексте следующего запуска.

---

## S17 — Per-user tool restrictions

**Предусловие**: Есть два аккаунта — обычный пользователь и admin

- [ ] Войти под обычным пользователем
- [ ] Попросить агента использовать admin-only инструмент (например, "Покажи список всех пользователей системы")
- [ ] Убедиться, что агент отказал или инструмент недоступен
- [ ] Выйти и войти под admin-аккаунтом
- [ ] Повторить запрос и убедиться, что admin видит расширенный набор инструментов и данных

**Ожидаемо**: Tool restrictions работают per-user, обычный пользователь не может использовать admin-only инструменты.

---

## S18 — Multi-channel session isolation

**Предусловие**: Пользователь подключён через Web Chat; Telegram-бот также настроен для того же аккаунта

- [ ] В Web Chat написать "Запомни: моё секретное слово — BANANA"
- [ ] Открыть Telegram и написать боту "Какое моё секретное слово?"
- [ ] Убедиться, что Telegram-сессия НЕ знает о BANANA (изоляция per_channel_peer)
- [ ] Вернуться в Web Chat и написать "Какое моё секретное слово?" — должен ответить BANANA
- [ ] Проверить в БД, что Web Chat и Telegram имеют разные session_id

**Ожидаемо**: Web Chat и Telegram — разные изолированные сессии, контекст не перетекает между каналами.

---

## S19 — Просмотр списка задач

**Предусловие**: Созданы несколько задач в разных статусах (active, recurring, completed)

- [ ] Написать в чат "Покажи мои задачи"
- [ ] Убедиться, что агент вернул список задач с именами и статусами
- [ ] Написать "Покажи только активные задачи" и убедиться в фильтрации
- [ ] Написать "Покажи задачи по расписанию" и убедиться, что recurring задачи показаны
- [ ] Убедиться, что в списке нет задач других пользователей

**Ожидаемо**: Агент корректно отображает список задач текущего пользователя с актуальными статусами.

---

## S20 — Audit trail — полная прозрачность

**Предусловие**: Создана и завершена (или упавшая) задача с известным ID

- [ ] Написать "Что произошло с задачей X?" (указать реальный ID или имя задачи)
- [ ] Убедиться, что агент вернул: время создания, время запуска, prompt отправленный в LLM
- [ ] Убедиться, что в audit есть: список вызванных tools, что ответила модель, duration выполнения
- [ ] Для упавшей задачи убедиться, что в audit есть описание ошибки
- [ ] Убедиться, что audit другого пользователя недоступен (403 при прямом API запросе чужой задачи)

**Ожидаемо**: Полный audit trail доступен через чат, содержит все детали выполнения, изолирован по пользователям.

---

## S21 — Pod kill + SSE reconnect (E31)

**Предусловие**: 2 инстанции приложения запущены (docker-compose с 2 репликами)

- [ ] Открыть чат в браузере, убедиться что SSE connected (DevTools → Network → EventStream активен)
- [ ] Создать долгую задачу (> 30 секунд): "Подожди 60 секунд и ответь"
- [ ] Убить под A: `docker stop <pod-a-container>` (найти имя через `docker ps`)
- [ ] Дождаться переподключения браузера к поду B (nginx round-robin, ~5-10 секунд)
- [ ] Дождаться завершения задачи и убедиться, что уведомление пришло через pod B

**Ожидаемо**: SSE переподключился, уведомление о завершении задачи пришло через pod B, данные не потеряны.
