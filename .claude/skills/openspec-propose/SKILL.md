Создать предложение на изменение спецификации.

Создам единый документ `change.md` — предложение + системные требования в одном файле.
После согласования запускай `/opsx:apply` для вливания в основную спецификацию.

---

**Input**: Название изменения (kebab-case) ИЛИ описание того, что нужно изменить.

**Steps**

1. **Этап 1: Интервью по задаче — понять ЧТО и ЗАЧЕМ**

   **НЕ создавай change.md после одного вопроса.** Сначала разберись в самой задаче, без привязки к коду и спецификациям.

   Начни с открытого вопроса:
   > "Какое изменение нужно внести? Опиши, что хочешь изменить и зачем."

   Затем задавай уточняющие вопросы по сути задачи:
   - **Мотивация**: "Какую проблему это решает? Кто столкнулся с ней?"
   - **Скоуп**: "Это затрагивает только один сервис или несколько? Какие?"
   - **Бизнес-логика**: "Какие правила должны работать? Есть ли исключения?"
   - **Ожидаемый результат**: "Как должно работать после изменения? Как пользователь это увидит?"
   - **Ограничения**: "Есть ли дедлайны, зависимости, технические ограничения?"

   **Правила этапа 1:**
   - Задавай вопросы порциями по 2–3, не заваливай стеной
   - Адаптируйся к ответам — если пользователь описал подробно, не переспрашивай очевидное
   - Если ответ неполный или противоречивый — копай глубже
   - **НЕ ПЕРЕХОДИ к этапу 2, пока суть задачи не ясна полностью**
   - Когда задача понятна — подведи итог и получи подтверждение

   Из описания выведи kebab-case имя — слова через дефис, маленькими латинскими буквами (напр. "добавить batch webhook отправку" → `add-webhook-batch`, "исправить валидацию email" → `fix-email-validation`).

2. **Изучи контекст**

   Прочитай:
   - Целевую спецификацию (ту, которую будем менять)
   - Связанные спецификации (если изменение затрагивает несколько сервисов)
   - Код сервиса — чтобы понять текущую реализацию

   **Справочные материалы** (поставляются с плагином в `references/`, рядом с `skills/`):
   - `references/common-requirements.md` — стандарты логирования, коды ошибок, RFC 7807 формат, маппинг HTTP-статусов
   - `references/analytics-rules.md` — правила оформления документации
   - `references/terms-and-abbreviations.md` — терминология
   - `references/example-change.md` — полный реальный пример заполненного change.md (636 строк, 18 критериев приёмки)

   **Анализ кода — используй лучшие доступные инструменты:**

   Проверь, какие инструменты анализа кода доступны, и используй наиболее эффективный из них (в порядке приоритета):
   1. **Serena** (MCP) — `find_symbol`, `get_symbols_overview`, `find_referencing_symbols` — семантический анализ, навигация по символам, поиск зависимостей
   2. **LSP-инструменты** — go-to-definition, find-references, workspace symbols — если доступен языковой сервер
   3. **Code index / embeddings** — семантический поиск по кодовой базе
   4. **Любые другие MCP-серверы или инструменты** для анализа кода, навигации, индексации — если доступны, используй
   5. **Grep/Glob** — текстовый поиск как последний вариант

   Не ограничивайся чтением отдельных файлов — строй полную картину: зависимости, вызывающий код, связанные сущности.

3. **Этап 2: Интервью по деталям реализации — КАК именно меняем**

   Теперь, зная задачу И изучив текущий код и спецификации, задавай вопросы по деталям реализации:
   - **Модели данных**: "Сейчас в сущности X есть поля A, B, C. Нужны новые? Что-то меняется?"
   - **Интеграции**: "Сервис сейчас вызывает Y и Z. Появляются новые вызовы? Меняются существующие?"
   - **Ошибки**: "Какие новые ошибки возможны? Как их обрабатывать?"
   - **Миграция**: "В таблице X сейчас N записей. Нужна миграция данных? Обратная совместимость?"
   - **Безопасность**: "Меняется доступ, роли, авторизация?"
   - **Конфигурация**: "Нужны новые параметры конфигурации? Feature-флаги?"
   - **Мониторинг**: "Нужны новые метрики или алерты?"

   **Правила этапа 2:**
   - Привязывай вопросы к конкретике из кода и спецификаций — "Сейчас работает так: ... Как это должно измениться?"
   - Если нашёл противоречия между задачей и текущей реализацией — обрати внимание
   - **НЕ ПЕРЕХОДИ к созданию файла, пока остаются неточности, неясности или недосказанности**
   - Когда все детали разобраны — подведи итог ВСЕХ собранных требований и явно спроси: "Всё ли учтено? Есть ли что-то, что я упустил?"
   - Только после подтверждения пользователя — переходи к созданию change.md
   - Если пользователь при подтверждении добавляет новые детали — обработай их и снова подведи итог

4. **Создай change-директорию**

   ```bash
   mkdir -p openspec/changes/<name>
   ```

   Если директория уже существует и в ней есть `change.md` — спроси пользователя: продолжить работу над существующим change или создать новый с другим именем.

5. **Прочитай шаблон change.md**

   Шаблон поставляется с плагином: `templates/change.md` (в корне директории плагина, рядом с `skills/`).
   Определи путь к шаблону по пути этого SKILL.md — поднимись на два уровня вверх и найди `templates/change.md`.

   Если шаблон в проекте (`openspec/schemas/analyst-driven/templates/change.md`) тоже есть — используй проектный, он имеет приоритет.

6. **Создай `change.md`**

   Заполни структуру реальными данными на основе изученного контекста:

   - Если используешь шаблон — **удали ВСЕ HTML-комментарии** (`<!-- -->`) и блоки `<!-- ПРИМЕР: ... -->`
   - Заполни метаданные в шапке (статус: Черновик, дата, целевая спецификация)
   - Для каждого из 13 разделов:
     - Если изменение затрагивает раздел — заполни реальными данными
     - Если не затрагивает — напиши ровно одну строку: `Нет изменений.`
   - Бизнес-правила — в формате ЕСЛИ/ТОГДА/ИНАЧЕ (примеры есть в шаблоне)
   - Рекомендации к критериям приёмки — в формате КОГДА/ТОГДА (примеры есть в шаблоне)
   - Для альтернативных и ошибочных сценариев используй цветовые маркеры:
     - `<font color="red">**Alt**</font>` — альтернативный/ошибочный поток
     - `<font color="blue">**Opt**</font>` — опциональный элемент
     - `<font color="blue">**Loop**</font>` — циклический элемент
     - `<font color="green">**Примечание:**</font>` — важные примечания

   **Уровни обязательности требований:**
   - ДОЛЖЕН / ОБЯЗАН — обязательно, система не работает без этого
   - СЛЕДУЕТ — рекомендуется, но допускается отступление с обоснованием
   - МОЖЕТ — опционально

   Запиши в: `openspec/changes/<name>/change.md`

   **ВНИМАНИЕ: большие файлы.** Change.md может получиться объёмным (200+ строк). Если файл большой — записывай его по частям (раздел за разделом), чтобы не потерять контент из-за ограничений контекстного окна. Предупреди пользователя: "Change объёмный, записываю по частям."

7. **Ревью в субагенте**

   После создания файла запусти ревью. Если доступен Agent tool — запусти **отдельный субагент**. Если нет — проведи ревью самостоятельно по чеклисту ниже.

   Промпт для субагента:
   > Проведи ревью файла `openspec/changes/<name>/change.md`.
   > Прочитай change.md, целевую спецификацию и код сервиса.
   > Проверь:
   > 1. **Полнота** — все ли аспекты задачи покрыты? Нет ли пропущенных разделов, которые должны быть заполнены?
   > 2. **Точность** — соответствуют ли описанные изменения реальному коду? Нет ли противоречий с текущей реализацией?
   > 3. **Непротиворечивость** — нет ли конфликтов между разделами внутри change.md?
   > 4. **Конкретность** — нет ли размытых формулировок, плейсхолдеров, TODO?
   > 5. **Реализуемость** — возможно ли реализовать описанное? Нет ли пропущенных зависимостей?
   > Верни список найденных проблем или "Ревью пройдено, замечаний нет".

   **Если субагент нашёл проблемы** — исправь change.md и сообщи пользователю, что было исправлено.

**Output**

После создания и ревью:
- Имя change и путь к файлу
- Краткое описание: какие разделы заполнены, какие — "Нет изменений"
- Целевая спецификация
- Результат ревью (замечания и исправления, если были)
- Подсказка: "Готово к согласованию. Для вливания в спецификацию — `/opsx:apply`"

**Guardrails**

**КРИТИЧНО — роль документа:**
- change.md — это документ СИСТЕМНОГО АНАЛИТИКА, а не разработчика
- Описывай ЧТО должно измениться и ЗАЧЕМ, но НИКОГДА не пиши КАК реализовать В КОДЕ
- **ЗАПРЕЩЕНО включать в change.md:**
  - Код на любом языке (Java, Python и т.д.)
  - Реализацию методов, классов, функций
  - Unit-тесты, integration-тесты, тестовый код
  - Конкретные алгоритмические решения (это задача разработчика)
  - План внедрения с техническими шагами реализации
  - Диаграммы классов или код-ревью
- **ПРАВИЛЬНО:**
  - Бизнес-правила в формате ЕСЛИ/ТОГДА/ИНАЧЕ (без кода)
  - Модели данных как таблицы полей (имя, тип, обязательность, пример значения, описание)
  - API как описание эндпоинтов (метод, путь, request/response схема), а не как реализация
  - Рекомендации к критериям приёмки в формате КОГДА/ТОГДА (без тестового кода)
  - Конфигурация как таблица параметров, а не как yaml/properties-файл
- SQL допустим ТОЛЬКО как рекомендации по DDL/DML (CREATE TABLE, ALTER TABLE) для описания структуры данных
- JSON-schema, Protobuf-определения, Avro-схемы допустимы для описания моделей данных
- Код приложения (Java, Python, Go и т.д.) ЗАПРЕЩЁН полностью
- Если пользователь просит добавить код — объясни, что change.md описывает требования, а реализация — задача разработчика на основе этих требований

**Процесс:**
- НИКОГДА не создавай change.md, пока остаются неясности — проведи полноценное интервью до полной ясности
- Перед созданием файла подведи итог ВСЕХ требований и получи явное подтверждение пользователя
- ВСЕГДА изучи целевую спецификацию ПЕРЕД созданием change.md
- НЕ копируй примеры из шаблона в итоговый файл
- Каждый заполненный раздел должен содержать реальные данные, а не плейсхолдеры
- Формулировки ДОЛЖЕН/ОБЯЗАН для обязательных требований
- Если change с таким именем уже существует — спроси, продолжить его или создать новый
- Проверь, что файл создан и содержит все 13 разделов
